# Hash, `action_key`, Ed25519 and manifest vectors

All four files are regenerated by `tools/build_vectors.py` from their descriptive fields
(inputs, derivations, seeds, messages, files).

## `sha256.json`

Inputs are `input_utf8` or a `generator` (`repeat`: `length` × `byte`; `affine`:
`byte[i] = (i*mul + add) & 0xff`). Hash one-shot and in uneven streaming chunks; one vector
crosses several 1 MiB chunks. Manifest `sha256` fields are bare lowercase hex; content ids
(a capture's manifest hash, an `action_key`) are `sha256:<hex>`.

## `action_key.json`

`valid[]`: a `derivation`, the canonical `preimage` built from it, and the `action_key`.
Implementations must reproduce both exactly. The rule is in
[spec/derivation-recipes.md](../../spec/derivation-recipes.md) R1. The cases show that
input order, `look`/`era`/`entry` labels, `tool`, `rank` and `eval` do not change the key,
and that `params`, `recipe.version`, `select`, `role` and adding an input do.
`invalid[]`: derivations that have no key (an input with zero or two content hashes, a
non-string hash, no `family`, no `recipe.version`, a model without `sha256`, non-object
`params`).

## `ed25519.json`

RFC 8032 §7.1 tests 1 to 3 plus one vector with seed bytes 0..31. Hex unless named
`*_b64`. Implementations derive `public_key` from `seed`, compute `key_id` (first 16 hex
digits of SHA-256 over the raw 32-byte public key), verify `signature` over `message`, and
must reject the signature with a bit flipped or over a modified message. `public_key_b64`
is standard base64 with padding, as in `manifest.signature.public_key`. Signers whose
signatures are randomised need only verify these, not reproduce them.

## `manifest.json`

A four-file package. Write `files` (UTF-8 `content`) into an empty directory package; build
the manifest with `top_level` fields and one entry per file (type, media and extra fields as
given; `sha256` and `bytes` computed; entries sorted by path in UTF-8 byte order); set the
signature block for the key with `seed`; canonicalise. The bytes must equal
`canonical_manifest`, their SHA-256 `manifest_sha256`, and `signature` (raw 64 bytes, hex
here) must verify over them. This vector tests hashing and signing only; its entries are
not a complete spec 1.1 file.
